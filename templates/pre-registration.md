# Pre-registration 模板 — 開跑前先寫定

> 本檔要在**開跑之前**寫完並 commit。跑完以後不能回頭改判斷標準；真的要改，就開一個新版本，把這一版留著。
> 這樣做是為了防最常見的自欺：先看結果，再挑一個能讓結果好看的判斷標準。

## 條件宣告（必填——結論只在這四個條件內成立）

| 條件 | 本次測量的值 |
|------|-------------|
| 模型 | {受測執行用哪個模型？評分用哪個模型？兩個都要填實際跑的值，不要填「預計」} |
| `harness`（AI 身上帶的整套環境設定：全域規則、記憶、其他 skill） | {跑測量的時候，環境裡還開著什麼？怎麼隔離的要寫具體，做法見下面的執行規則} |
| 任務分佈 | {題目覆蓋哪些任務型態？沒覆蓋到的型態，結論原理上就不能外推過去} |
| 使用者既有能力 | {prompt 裡自帶了多少規矩？使用者（或題目）本來的習慣，等於一層看不見的 `harness`。對照組拿到的規則句要逐字列出} |

## 受測物

- skill：{名稱＋版本快照（commit hash 或日期）。模型與 skill 都會更新，凍結不了就把版本記下來}
- 類型（必填，決定後面判斷標準怎麼設計）：
  - **產出物型**：做出來的是檔案或頁面。判斷標準可以寫成機器檢查得了的條件，下面的四類檢查項直接用。
  - **方法注入型**：改的是 AI 做事的方式，效果散在過程裡，看不到單一產物。判斷標準用它官方說明裡自己宣稱的效果，逐字引用。「使用方式照官方說明設置」歸前置檢查，並逐字記錄。
  - **互動型**：產出是一整場對話，只能靠 AI 讀對話品質評分，主觀成分最重。效果會跟著使用者本來的能力浮動，「在誰身上測」影響最大。
  - **其他**：先描述產出長什麼樣，再決定判斷標準的形式。
- 預期效果的依據：{預設引用 skill 自己的宣稱與 description。測的是：它宣稱的效果，在你的條件下有沒有出現。這是最不武斷的標準：規格是 skill 作者自己給的，沒人能指控出題偏頗。但書：這個標準回答不了「你的工作流裡值不值得用它」。你的日常可能根本碰不到它宣稱的場景。要測那個，題目要改從你的真實使用場景出，並在報告裡寫明兩者的差別}
- 兩組跑法（醫學試驗叫「兩臂」）：一組給 skill，一組不給，其餘完全一樣。
  - 給 skill 這一組拿到：{逐項列——skill 全文？skill 連帶載入的其他東西？}
  - 對照組拿到：{逐項列。**誠實檢查：對照組是不是真的「沒有 skill」？** 如果 prompt 含 skill 的核心規則句，你測到的就是殘餘差值。材料本身若就是 skill 某一步的產物，也一樣。現在就寫下來，不要等跑完才發現}

## 題組

| # | case 檔 | 型 | 來源（真實摩擦） |
|---|---------|-----|----------------|
| | | | |

題組健檢：有沒有乾淨對照題（測「會不會把好的改壞」）？有沒有負向對照（測誤觸發）？要不要放壓力測試位？可以模擬時限壓力、或上級說「先跳過」，藉口要逐字留檔。做法致意 [skill-forge](https://github.com/neokn/skill-forge)。

## 四類檢查項（斷言：一條能直接判對錯的檢查句）

| 類別 | 算不算分 | 本次內容 |
|----|-----------|---------|
| 前置檢查（gate） | ❌ 不計分。任一沒過，這一次 run 就算 invalid，要補跑。 | {格式、語言、能不能獨立看懂，這種「照著模板抄就會過」的項目全歸這一類。拿去算分等於送分，測不出任何差別} |
| 事實檢查 | ✅ 算分。逐項二元判定，附證據位置。 | {不捏造識別碼／日期／出處、不把推測寫成事實…} |
| 判斷檢查 | ✅ 算分。逐項二元判定。 | {不代替裁決者下結論、不擅自標記推薦…} |
| 取向觀察 | ❌ 不計分，但強制記錄。 | {二元判斷標準抓不到的風格與取向差異；原始輸出一律留存} |

## 規模

{題數} × 2 配置 × {每配置 run 數} ＝ {總 run 數}。
小規模下，加重複次數通常比加題目划算。設了幾就跑滿幾——設 3 跑 1 的數據不要用。

起跳建議：3 題 × 2 組 × 3 run，一共 18 次。開跑前，先把時間抓一下。viz-explain v2 實測：帶 skill 那組每次中位數 383 秒。不帶那組 127 秒。帶 skill 那組，每次輸出大約 3 萬個 `token`（輸出字數）。

## 可說明／無法說明（先寫死）

- **可說明**：{描述性、僅限本次 run 的話}
- **無法說明**：{因果通則／外推到題組外任務／跨模型比較／…——現在寫，跑完照著念}

## 執行規則

1. fresh session、乾淨 workspace，每個 run 分開跑。彼此不互相干擾。
2. 環境隔離：採 skill-forge cli-executor 的做法。並依 2026-08-17 兩機的已知答案探針結果修正。可以直接照抄的指令，見 README「怎麼跑一次量測」。
   - **選目錄**：挑一個不在家目錄底下的暫存目錄。這個目錄和它每一層的上層目錄都不能有 `.claude/`。
   - **放 skill**：把受測 skill 放進這個目錄的 `.claude/skills/`。
   - **執行時三件一起給**：`--setting-sources project`、`--strict-mcp-config`，加上環境變數 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`。前兩個旗標管不到自動記憶——官方文件寫明了這件事，不加第三個，記憶照樣會被載入。兩組用到的旗標與環境變數要一樣。

   為什麼要挑不在家目錄底下、且上層沒有 `.claude/` 的目錄？`project` 這個設定來源，會把上層目錄的 `.claude/rules/*.md` 一併當成專案規則載入。mac 的 `$TMPDIR`（在 `/var/folders/…` 底下）可以用。Windows 的 `%TEMP%` 在使用者目錄底下，不能用。

   - **用前先做已知答案檢查**：同一個目錄、問同一句話，跑兩次，差別在有沒有加上面那三件。沒加的那一次，要讀得到你指定的一條全域規則；加了的那一次，要讀不到。只跑「讀不到」那一次沒有意義。沒有「同目錄讀得到」的對照，證明不了是那三件的功勞。檢查結果反過來的話，先停下來，回頭查上層目錄是不是還留著 `.claude/`，不要繼續往下跑。

   目前已驗過的已知答案題（canary）：
   - 一條 user rule
   - 一個 user skill
   - 一個 user hook
   - auto-memory 索引

   MCP 還沒設已知答案題，不在已驗範圍內。
3. 對照組的誠實檢查：確認對照組不只是「沒用 skill」。而是「skill 根本不在可用清單上」。skill 在清單上卻沒被用到，測到的差距會偏樂觀，不是乾淨的差值。
4. gate 不過的 run 記 invalid，補跑（逐字相同 prompt）。不算失敗也不算通過。
5. 評分模型欄位要實填，不留佔位符。
6. 跑完先填 results（數據），才可以寫任何結論。結論怎麼說，受「可說明／無法說明」約束。
