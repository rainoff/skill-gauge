# Case 模板 — 單一題目

> 一條真實摩擦（friction）對應一個 case。複製本檔，逐欄填寫。
> 「Baseline 對照」與「負向對照」是必備欄位，不可留空——這是本 repo 的設計裁決。

```yaml
---
id: {編號}-{slug}
skill: {受測 skill 名稱與版本快照（commit hash 或日期）}
added: {YYYY-MM-DD}
source: {為什麼有這一題——哪一次真實摩擦或翻車。「想到的」不是來源}
source_ref: {連到那次真實摩擦的證據：對話紀錄、issue、檔案路徑；沒有就寫「口述」}
type: {陷阱題 / 乾淨對照題 / 來源紀律題 / 壓力測試題 / …}
---
```

## Scenario

{什麼情境？給受測者的 prompt 與材料，寫在這裡或附檔。注意：兩組拿到的 prompt 與材料必須逐字相同，差異只在 skill。}

## Baseline 對照

{不帶 skill 的時候，同樣情境下模型會做出什麼，先寫在這裡。要先確認模型本來就做不到、或者做得不穩，之後 skill 的效果才算得到它頭上。模型原生就會做的事，加上 skill 只是多花錢多花時間。怎麼確認的也寫一行：哪一次不帶 skill 的實跑、或連結。}

## 負向對照

{不該觸發的鄰近場景。在這些場景觸發，就算誤觸發，直接 FAIL。觸發語寫得越寬，這一欄越重要。}

## 怎樣算通過

{寫清楚怎樣才算通過。每一條前面標上 [結果] [流程] [風格] [效率] 其中一類。設計的時候，四類各問一次「這一類要不要測」。有一種寫法要特別小心：「如果引用了 X，就必須…」這種帶條件的判斷標準。這會讓完全不做 X 的產出自動通過，等於在獎勵迴避。能改寫成正面要求的，就改成正面要求。}

- [效率] {…}（範例，換成你的：產出不超過逐字稿長度的一半）

## Run method

{怎麼重跑？把 fresh session、隔離環境設定、指令都寫清楚。要具體到別人照著就能重現。照 README「怎麼跑一次量測」的指令即可，把用到的參數抄在這裡。}
